# DNS enforcement

Every DNS query from the LAN VLANs and from WireGuard (`wg0`) is answered by
AdGuard Home (AGH) on the router. This holds even when a device is set by
hand to another resolver (8.8.8.8, 1.1.1.1, ...). Encrypted DNS that cannot
be redirected (DoT, DoQ, DoH to known resolvers) is rejected, and AGH logs
each client's real address.

Brume 2 could not do this, because client traffic did not pass through it.
Custos is the edge router behind the ISP router, so all client traffic
passes through its forward and prerouting hooks.

## Layers

| # | Mechanism | Where | Stops |
|---|-----------|-------|-------|
| 1 | DHCP hands out the VLAN gateway (192.168.<n>.1) as DNS | `custos-network` (`CUSTOS_LAN_DNS` empty) | well-behaved clients |
| 2 | `dstnat`: udp/tcp 53 from `br-lan.*`/`wg0` to *any* address → `redirect to :53` | `10-dns-enforce.nft` | hard-coded plain DNS (8.8.8.8, ...) |
| 3 | `dns_guard`: reject tcp/udp 853, 784, 8853 | `10-dns-enforce.nft` | DoT, DoQ |
| 4 | `dns_guard`: reject tcp/udp 443 to `@doh_v4` | `10-dns-enforce.nft`, `11-doh-v4.nft` | DoH / DoH3 to known resolver IPs |
| 5 | AGH blocks DoH/VPN/proxy host names (HaGeZi `doh-vpn-proxy-bypass`) | `AdGuardHome.yaml` | DoH resolvers found by name |
| 6 | `use-application-dns.net` → NXDOMAIN | AGH user rule | Firefox turning on its own DoH |
| 7 | `mask.icloud.com`, `mask-h2.icloud.com` → NXDOMAIN | AGH user rule | iCloud Private Relay |
| 8 | Forwarded IPv6 from clients dropped | `dns_guard` | any IPv6 path (see below) |

**Redirect, not drop.** A client that asks 8.8.8.8 gets an answer that looks
like it came from 8.8.8.8 (conntrack reverses the NAT on the reply). That
answer is filtered. Nothing breaks visibly, and the client has no reason to
look for a bypass. With a drop, the client would fail and try the next
method (often DoH).

**Reject, not drop, for DoT/DoQ/DoH.** A TCP reset or ICMP port-unreachable
makes the client fall back to plain DNS at once (seconds, not a timeout),
and the redirect catches that fallback.

**Real client IP.** `redirect` changes only the destination address, so AGH
sees `192.168.<n>.x` as the source. No proxying, no EDNS Client Subnet.

**Fail closed.** If AGH is not running, the redirect still applies, and
client DNS fails rather than reaching an unfiltered resolver. The firewall
loads before networking (`custos-firewall.service`, A2).

## Rule placement

`/etc/custos/firewall.nft` (base table, A2) declares an empty `dns_guard`
chain, calls `jump dns_guard` from `forward` for `$DNS_IFS` before the
LAN→wan accept, and at the end has
`include "/etc/custos/firewall.d/*.nft"`. The fragments add to the same
table in the same `nft -f` transaction, so a reload is still atomic.

```
firewall.d/10-dns-enforce.nft   set doh_v4 (declaration), chain dstnat, rules of dns_guard
firewall.d/11-doh-v4.nft        add element inet custos doh_v4 { ... }   (package custos-firewall-doh)
```

The router's own traffic (AGH → Quad9/Mullvad DoH, bootstrap 9.9.9.9 and
194.242.2.2) goes through `output`, not `forward`. The DoH set therefore does
not block AGH's upstreams, even though those addresses are in the list.

## The doh_v4 set

* Source: HaGeZi `ips/doh.txt` (IPv4 addresses of public DoH resolvers),
  pinned to commit `HAGEZI_REV` in `custos-firewall.bb` with a sha256sum.
  The current pin has 1476 entries.
* Build: `do_install` keeps only IPv4 addresses/prefixes, removes
  duplicates, and writes `11-doh-v4.nft`. The build fails if nothing is
  left. The set has `flags interval; auto-merge`, so prefixes and
  overlapping entries are fine.
* Update on the device (later, `custos-apply`): rewrite
  `/etc/custos/firewall.d/11-doh-v4.nft` in the same format, then
  `systemctl reload custos-firewall`. The file is a CONFFILE.
* Updating the pin: change `HAGEZI_REV` and both sha256sums
  (`bitbake -c fetch custos-firewall` prints the new values).
* Limits: the list covers resolvers known by IP. A DoH server on a shared
  CDN address, or on a private one, is not on it. Layer 5 (host names in
  AGH) covers those found by name. A client that ships its own DoH server
  *and* hard-codes its IP can still get through. That is accepted and
  documented here; TLS interception would be needed to close it, and it is
  out of scope.

The router itself resolves through `CUSTOS_WAN_DNS` (Quad9 9.9.9.9 and
149.112.112.112; `/etc/resolv.conf` → `/run/systemd/resolve/resolv.conf`),
not through the ISP router, whose DNS proxy did not answer on the
development line (which also stopped NTP). Only clients are forced through
AGH.

## IPv6

Clients get no IPv6 today: the VLAN interfaces have
`LinkLocalAddressing=no` and `IPv6AcceptRA=no`, there is no RA or DHCPv6
server, IPv6 forwarding is off (no `net.ipv6.conf.all.forwarding`), and
`dns_guard` drops every forwarded IPv6 packet from `$DNS_IFS` (counted). The
`dstnat` redirect is in an `inet` table, so it already applies to IPv6 DNS
to the router.

**Before IPv6 is enabled for clients**, all of the following must be in
place, or DNS leaks over IPv6:

1. A `doh_v6` set (`type ipv6_addr; flags interval; auto-merge`) filled from
   an IPv6 DoH list, plus
   `ip6 daddr @doh_v6 tcp dport 443 reject with tcp reset` and
   `ip6 daddr @doh_v6 udp dport 443 reject` in `dns_guard`.
2. The DoT/DoQ port rules stay as they are (they match both families).
3. The redirect needs a router address on each VLAN for IPv6 (the target of
   `redirect` is the primary address of the incoming interface), and AGH
   must listen on `::` (`bind_hosts`).
4. RA/DHCPv6 must announce the router's IPv6 address as DNS (RDNSS).
5. Only then remove `meta nfproto ipv6 ... drop` from `dns_guard`, and
   extend `tests/S11-dns.sh` with the same checks over IPv6.
